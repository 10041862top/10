    Book-to-Skill 轉換器¶

    透過提取結構（而非產生摘要），將書面知識轉換為可執行的 agent skills。

    理念¶

    書籍包含了結晶化的專業知識：歷經多年發展的框架、原則與技巧。此 skill 將這些知識提取為 GitHub Copilot CLI、Amp、Claude Code 或其他相容 agent 可以重複利用的格式。

    提取結構，而非摘要。 skill 不是讀書心得報告。它是一個工具包，包含： - 具名的框架（具有明確應用場景的心智模型） - 可執行的原則（指導決策的規則） - 技巧（循序漸進的方法） - 反模式（應該避免什麼以及原因） - 語氣校準（作者如何思考與溝通）

    保留作者的精準度。 框架通常有特定的命名原因。「The 5 Whys」不能替換為「ask why multiple times」。請捕捉確切的表述。

    適當的分層深度。 簡單的書籍 → 簡單的 skills。具有 10 個以上框架的複雜書籍 → 帶有參考檔案與按需載入章節的 skills。

    運作模式¶

    提供四種路徑。根據使用者的要求進行路由：

    1. 完整轉換 (預設)¶

    觸發條件： 使用者提供一個或多個文件/目錄/glob 路徑，且沒有特殊指示 動作： 執行下方所有步驟 (步驟 0–9) 輸出： 完整的 skill，包含 SKILL.md、chapters/、術語表 (glossary)、模式 (patterns)、備忘錄 (cheatsheet)

    2. 僅分析 (Analyze Only)¶

    觸發條件： 使用者說「分析」、「只需提取」，或「我想在生成前先檢閱」 動作： 執行步驟 0–3，然後產生結構化的提取報告（找到的框架、原則、技巧）。停止 — 不要生成 skill 檔案。 輸出： 供使用者檢閱的分析報告

    3. 從先前的分析生成¶

    觸發條件： 使用者有現有的分析筆記，或先前已執行過僅分析 動作： 跳過步驟 0–3，使用提供的分析作為輸入，執行步驟 4–9 輸出： 從提供的分析生成的 skill 檔案

    4. 更新 / 融入 (現有的 Skill)¶

    觸發條件： 使用者提供一個或多個新來源路徑，並表明他們想要更新現有的 skill（無論是指向現有 skill 資料夾、提供 SKILLS_HOME 中已存在的 skill slug，或是明確要求更新）。 動作： 執行步驟 0（範圍外檢查）、步驟 1（驗證輸入）、步驟 1.5（識別書籍類型），以及步驟 2（提取新檔案）。接著跳至步驟 5（識別/偵測現有 skill 路徑）並執行 更新 / 融入 Workflow 以將新內容合併到現有的 skill 檔案中。 輸出： 更新後的現有 skill，包含新增/修改的章節摘要與合併的索引/術語表。

    Skill 位置¶

    此轉換器可以從多個 skill 系統執行。在尋找此轉換器的輔助指令碼或寫入生成的書籍 skill 時，優先選擇以下位置：

    1. GitHub Copilot CLI 個人 skills: ~/.copilot/skills/
    2. 跨 agent 個人 skills (Copilot, Amp, Codex): ~/.agents/skills/
    3. Claude Code 個人 skills: ~/.claude/skills/
    4. 專案本機 Copilot skills: .github/skills/
    5. 專案本機 Claude skills: .claude/skills/
    6. 專案本機 Amp / Copilot skills: .agents/skills/
    7. Amp 全域 skills: ~/.config/agents/skills/
    8. Amp 舊版全域 skills: ~/.config/amp/skills/

    對於生成的書籍 skills，請挑選使用者主機 agent 實際能發現的目的地 (請見步驟 5)。如果存在多個有效的根目錄，請詢問使用者一次，並在工作階段中記住答案 — 不要默默地使用預設值。

    步驟 0 — 範圍外檢查¶

    如果未提供任何參數，請停止並回應：

    "book-to-skill requires a supported document path, folder, or glob pattern. Usage: book-to-skill <path-to-document-folder-or-glob>... [skill-name-slug]"

    在整個 workflow 中： - 識別輸入路徑與可選的 skill slug。 - 如果最後一個參數不是存在的檔案、資料夾、或符合任何檔案的 glob，且它看起來像一個 skill slug（例如，小寫連字號、英數字），則將其視為 SKILL_NAME。 - 將所有其他參數視為 INPUT_PATHS 列表。 - 如果任何輸入路徑是現有的 skill 目錄（包含 SKILL.md 和 chapters/ 子資料夾），或如果 SKILL_NAME 與 SKILLS_HOME 中現有的 skill slug 相符，則將此執行標記為 更新/融入 (Update/Fold-in) 操作 (模式 4)。

    步驟 1 — 驗證輸入¶

    驗證 INPUT_PATHS 中至少有一個支援的檔案、目錄或 glob 模式。 對於目錄和 glob，將其展開以尋找符合的支援檔案（.pdf、.epub、.docx、.txt、.md、.markdown、.rst、.adoc、.html、.htm、.rtf、.mobi、.azw、.azw3）。

    如果找不到支援的檔案，請停止並提供明確的錯誤訊息。

    步驟 1.5 — 識別內容類型¶

    在提取之前，請詢問使用者：

    "What kind of content do these sources have? This helps me choose the best extraction method.

    1. Technical — 有程式碼區塊、表格、公式、圖表（例如程式設計書籍、學術論文、架構指南）
    2. Text-heavy — 大部分是散文，很少或沒有表格/程式碼（例如管理、生產力、敘事性非小說類）
    3. Not sure — 我將使用快速方法，如果品質似乎有限，會提醒您"

    將答案儲存為 BOOK_TYPE： - 選項 1 → BOOK_TYPE=technical - 選項 2 → BOOK_TYPE=text - 選項 3 → BOOK_TYPE=text

    如果 BOOK_TYPE=technical，在繼續前通知使用者：

    "📐 Technical mode selected — 使用 Docling 進行結構感知提取（保留為 markdown 的表格、程式碼區塊、公式）。這大約需要每頁 1.5 秒，所以較長的來源預計需要幾分鐘時間。現在開始…"

    如果 BOOK_TYPE=text，通知：

    "📄 Text mode selected — 為每種檔案類型使用最快適合的提取器。純文字/Markdown/HTML 通常在幾秒鐘內準備就緒；PDF 會在可用時使用 pdftotext。"

    步驟 2 — 從來源文件提取文字¶

    執行提取指令碼，傳遞輸入路徑：

    SCRIPT_PATH=""
for candidate in \
  "$HOME/.copilot/skills/book-to-skill/scripts/extract.py" \
  "$HOME/.agents/skills/book-to-skill/scripts/extract.py" \
  "$HOME/.claude/skills/book-to-skill/scripts/extract.py" \
  ".github/skills/book-to-skill/scripts/extract.py" \
  ".claude/skills/book-to-skill/scripts/extract.py" \
  ".agents/skills/book-to-skill/scripts/extract.py" \
  "$HOME/.config/agents/skills/book-to-skill/scripts/extract.py" \
  "$HOME/.config/amp/skills/book-to-skill/scripts/extract.py"
do
  if [ -f "$candidate" ]; then
    SCRIPT_PATH="$candidate"
    break
  fi
done

if [ -z "$SCRIPT_PATH" ]; then
  echo "Could not find scripts/extract.py for book-to-skill" >&2
  exit 1
fi

PYTHON_BIN="${PYTHON_BIN:-python3}"
if ! command -v "$PYTHON_BIN" >/dev/null 2>&1; then
  PYTHON_BIN="python"
fi

"$PYTHON_BIN" "$SCRIPT_PATH" $INPUT_PATHS --mode <BOOK_TYPE> --install-missing ask

    在提取之前，指令碼會檢查偵測到的格式所需的選用 Python 套件。如果缺少更好的提取器，它會提示使用者提供可用的後備選項。非互動式工作階段預設為後備選項，除非明確將安裝模式設為 yes。

    提示 — 環境預檢： 執行 "$PYTHON_BIN" "$SCRIPT_PATH" --check 列印每種格式已安裝提取器的報告，以及安裝缺少項目的確切指令，而不處理任何檔案。當使用者報告設定或品質問題時很有用。

    這會建立： - <tempdir>/book_skill_work/full_text.txt — 合併所有來源提取的文字，並具有清晰視覺區分的邊界。 - <tempdir>/book_skill_work/metadata.json — 整體合併的大小、字數、頁數、token 數量、捨棄的 EPUB 圖片數量，以及詳細處理過 sources 的列表。

    讀取 <tempdir>/book_skill_work/metadata.json 以檢查結果。

    步驟 2.5 — 預檢成本估算¶

    讀取 <tempdir>/book_skill_work/metadata.json 並在進行任何生成之前向使用者展示估算：

    📖 偵測到來源: <total_sources> 來源
<列出 metadata 清單中的每個來源檔案名稱和格式>
<如果 images_dropped > 5: 警告有 N 個來源圖片未被讀取>
📄 合併的頁面/章節: ~<N> | 字數: ~<N> | 總 tokens: ~<N>K

💰 估計的 token 成本 (完整轉換 / 更新):
   輸入  (讀取 + prompts): ~<N>K tokens
   輸出 (生成/更新的 skill 檔案):  ~<N>K tokens
   總計:                           ~<N>K tokens

   成本: 將上述 token 數乘以您的模型目前的
   每 100 萬 token 輸入/輸出費率（價格和模型名稱經常變動 —
   請勿寫死；引用今天的費率並將其標記為估算值）。

   ⏱  預估時間: ~<N> 分鐘

📁 將生成/更新的檔案:
   SKILL.md + chapter 檔案 + glossary + patterns + cheatsheet

➡  繼續完整轉換 / 更新？ (或輸入 "analyze only" 先行預覽)

    如何估算： - 輸入 tokens ≈ metadata 中的 estimated_tokens × 1.3 (每章節傳遞的 prompts 額外負擔) - 輸出 tokens ≈ 章節數 × 每章預算 + 4,000 (SKILL.md) + 4,500 (glossary + patterns + cheatsheet) - 根據 BOOK_TYPE 決定每章預算中位數 (DEPTH 在步驟 4 決定，可能會提高它)：text ≈ 1,000，technical ≈ 1,800。如果使用者已經指出是僅參考還是深入學習，則使用步驟 7 矩陣的對應列。 - 成本：報告 token 數量並將其乘以使用者目前的每 100 萬 token 輸入/輸出費率。不要寫死具體金額 — 模型名稱和價格會變動；如果您顯示，請標記為估算並註明日期。

    等待使用者確認後再繼續。如果他們說 "analyze only"，則切換到模式 2。

    步驟 2.6 — 大型書籍（> 5 萬 tokens）的 REPL 風格存取¶

    受到遞迴語言模型 (RLM) 典範的啟發：將 full_text.txt 視為可查詢的語料庫，而不是一次性讀取。將整個檔案載入上下文中，會耗盡您稍後生成所需的預算。

    對於超過約 5 萬 tokens 的書籍，偏好使用程式設計方式探測，而不是沒有邊界的 Read(full_text.txt)：

    # 在任何 Read 之前檢查大小
wc -w "$FULL_TEXT_PATH"

# 尋找章節偏移量而不載入整個檔案
grep -n -E "^\s*(Chapter|CHAPTER)\s+[0-9]+" "$FULL_TEXT_PATH" | head -40

# 僅拉取您需要的章節（包含開始到結束行）
sed -n '<start>,<end>p' "$FULL_TEXT_PATH"

# 在在 SKILL.md 宣告之前驗證框架確實被提及
grep -c -i "westrum\|dora" "$FULL_TEXT_PATH"

# 具有偏移量/限制的目標 Read 避免傾印完整檔案
# Read(file_path=full_text.txt, offset=<line>, limit=<lines>)

    針對步驟 3（結構分析）、步驟 7（每章摘要）與步驟 8（glossary / patterns 提取）使用這種方法。在不到 5 萬 tokens 的書籍上，單次 Read 就可以了。

    為什麼這很重要：一本 200 頁的書約有 7.5 萬個 tokens。每章重讀一次（28 次）花費約 200 萬個輸入 tokens；使用 grep + sed 僅提取相關的片段可保持生成成本與輸出成正比，而不是與來源成正比。

    步驟 3 — 分析書籍結構¶

    讀取提取的 full_text.txt 的前 8,000 個字元來識別： - 書籍標題 (title) 與作者 (author(s)) - 章節結構（尋找 "Chapter N"、"PART I"、編號標題、目錄） - 核心主題與學科領域 - 大致章節數量

    然後閱讀目錄部分（如果有的話）以映射所有章節。

    如果模式為「僅分析 (Analyze Only)」： 現在產生提取報告並停止。結構： 

    ## 提取報告 — <Title>

### 作者核心框架 (Author's Core Frameworks)
- **<Framework Name>**: <它是什麼以及何時應用>

### 關鍵原則 (Key Principles)
- <Principle>: <可執行的規則>

### 技巧與方法 (Techniques & Methods)
- <Technique>: <循序漸進或操作指南>

### 反模式 (Anti-patterns)
- <要避免什麼>: <為什麼>

### 建議的 Skill 名稱
`{author-lastname}-{core-concept}` — 例如 `cialdini-influence`

### 偵測到的章節 (Chapters Detected)
| # | 標題 | 主要框架 |

    步驟 4 — 詢問目的 (僅限完整轉換)¶

    在生成之前，請詢問使用者：

    "What should this skill help you do? (Pick one or more) 1. Apply the author's frameworks while working 2. Think with the author's mental models 3. Reference specific chapters and concepts 4. All of the above"

    使用答案來權衡在 SKILL.md 核心 (Core) 部分要強調的內容。

    根據答案衍生 DEPTH（沒有額外的 prompt）： - 答案僅為選項 3 (參考) → DEPTH=reference — 精簡、快速查詢的章節。 - 答案包含選項 1、2 或 4 → DEPTH=study — 更深入的章節，包含更多實際詳細資訊、範例與推論。

    DEPTH 和 BOOK_TYPE 共同在步驟 7 中設定每章 token 預算。不要單獨詢問「學習與參考 (study vs reference)」的問題 — 它是在此處推斷出來的。（在跳過步驟 4 的模式 2/3 中，預設 DEPTH=study。）

    步驟 5 — 決定 skill 名稱¶

    如果提供了 SKILL_NAME，則將其用作 skill slug。 否則，提出兩個選項讓使用者選擇： - 按作者-概念: {author-lastname}-{core-concept} (例如 cialdini-influence, meadows-systems) - 按標題: 書名的連字號小寫 (例如 designing-data-intensive-apps)

    如果該書具有強烈的方法論特徵，則預設採用作者-概念格式。

    選擇目的地 skill 根目錄 (SKILLS_HOME)。探測使用者檔案系統以尋找現有 skill roots，並由使用者正在執行的主機挑選：

    Host agent 個人 skill root (依序探測) 專案本機 root
    GitHub Copilot CLI ~/.copilot/skills → ~/.agents/skills .github/skills → .claude/skills → .agents/skills
    Amp ~/.agents/skills → ~/.config/agents/skills → ~/.config/amp/skills .agents/skills
    Claude Code ~/.claude/skills .claude/skills
    OpenAI Codex ~/.agents/skills (原生發現; 遵循符號連結) .agents/skills

    步驟 7 — 生成章節摘要¶

    TOKEN 預算規則 — 關鍵 (自適應)：

    每章的預算隨著 BOOK_TYPE 與 DEPTH 進行縮放。技術章節需要空間放置程式碼與表格；學習深度需要空間放置推論過程。從此矩陣中挑選預算：

    DEPTH=reference DEPTH=study
    BOOK_TYPE=text 800–1,200 tokens 1,000–1,800 tokens
    BOOK_TYPE=technical 1,200–1,800 tokens 2,000–3,000 tokens
    • 這些是單檔的目標，而不是硬性上限 — 密集的章節可能會超出，稀疏的章節可能會低於目標。密度仍勝於長度（品質規則 #3）：絕不為了達到數字而填補內容。
    • 檔案是按需載入的，所以較大的章節只有在實際閱讀該章節時才會花費 tokens。
    • 介於兩個儲存格之間（例如混合內容書籍）若有疑問，使用較低的預算，並讓深度來自精確度，而不是份量。

    DEPTH=study 必須以內容來爭取，而不是用更大的數字。 標準小節範本 (Core Idea → Connects To) 自然會將密集散文章節的字數落在約 700–900 tokens 左右。若要真實地達到學習預算（不是透過填補內容），研究深度章節必須增加具體的材料： - 從該章節重現一個實際範例或工件（例如範例新聞稿、範例對話、填寫好的範本、作者演練的決策），置於 ## Worked Example 標題之下。這是最大的槓桿，也是學習者回頭尋求的主要內容。 - 將每個框架的「如何做 (How)」展開為明確的步驟或標準，而非單行敘述。 - 針對前 1–2 個框架加入簡短的「為什麼有效 / 失敗模式」附註。

    如果一章確實沒有實際範例且難以擴充，就讓它低於學習預算的下限，而非強行填補內容 — 並註明該章的核心概念較為單薄。相較之下，reference 深度的章節會刻意省略實際範例，僅保留準備好可供決策的精華。

## 步驟 8 — 產生支援檔案

### glossary.md
建立 `$SKILLS_HOME/<skill_name>/glossary.md`:
- 來自書籍的每個重要術語，按字母排序
- 格式：`**Term** — 定義 (Ch N)`
- 最大 1,500 tokens

### patterns.md
建立 `$SKILLS_HOME/<skill_name>/patterns.md`:
- 來自書籍的所有具體技巧、設計模式、演算法
- 格式：`## Pattern Name\n**When to use**: ...\n**How**: ...\n**Trade-offs**: ...`
- 最大 2,000 tokens

### cheatsheet.md
建立 `$SKILLS_HOME/<skill_name>/cheatsheet.md`:

**這是 skill 中最具差異化的一層 — 請將其視為推論的輔助工具，而非關鍵字列表。** 任何人都能夠在術語表中 grep 搜尋詞彙。備忘錄記錄的是作者的**判斷力**：他們會做出什麼決定以及原因。這是將「我懂得這些詞」轉化為「我會像作者那樣行動」的檔案。

優先順序：
1. **決策規則 (Decision rules)** — 「當 X 時，做 Y，因為 Z」。作者應用的 if/then 邏輯，並以讀者不需重讀書籍即可套用的方式陳述。
2. **決策樹 (Decision trees) / 流程圖 (flowcharts)** (作為巢狀項目符號或小型表格) — 用於多於兩個分支的選擇。
3. **權衡矩陣 (Trade-off matrices)** — 在作者關心的維度上對相互競爭的選項進行評分，讓讀者可在自身限制下進行選擇。
4. **閾值 (Thresholds) & 預設值 (defaults)** — 作者承諾的具體數字、比例或經驗法則（例如「將函數保持在 20 行以內」，「當錯誤預算 < 10% 時發出警報」）。
5. **跡象 (Tells) & 氣味 (smells)** — 用於辨識狀況的快速啟發法 (heuristics)（「如果您看到 X，您可能遇到了麻煩 Y」）。

避免：僅有 詞彙→定義 的列表（那是術語表），以及散文段落（那是章節）。每一行都應該幫助讀者**決定**某些事。

- 大多數格式化為精簡的表格和決策規則；您會希望將其放在單一列印頁面上並在工作時放在身邊的內容。
- 最大 1,200 tokens。

id="__codelineno-12-1" name="__codelineno-12-1" href="#__codelineno-12-1"></a>⚠️ Published from a copy: <skill folder> sits inside another git repository, so it has <a id="__codelineno-12-2" name="__codelineno-12-2" href="#__codelineno-12-2"></a> no remote of its own. To publish a later update, re-run Step 11, or clone <a id="__codelineno-12-3" name="__codelineno-12-3" href="#__codelineno-12-3"></a> https://github.com/<owner>/<repo_name> and fold new material into the clone. </code></pre></div> <p>根層級 <code>SKILL.md</code> 的佈局與 <code>skills</code> CLI 偵測到的完全相同，因此儲存庫可以直接安裝 — 不需要重組。在巢狀儲存庫以外的情況下，本機資料夾保留為此機器的實時安裝，並且是遠端的工作複本，因此後續的 Update/Fold-in 執行可以將它們的變更 commit 並 push 到同一個遠端。</p> <hr /> <h2 id="update-fold-in-workflow">更新 / 融入 (Update / Fold-in) Workflow<a class="headerlink" href="#update-fold-in-workflow" title="Permanent link">¶</a></h2> <p>對位於 <code>$SKILLS_HOME/<skill_name>/</code> 的現有 skill 執行 更新/融入 (Update/Fold-in) 操作時：</p> <h3 id="1-skill">1. 讀取現有 Skill 結構<a class="headerlink" href="#1-skill" title="Permanent link">¶</a></h3> <p>讀取並解析現有 skill 的檔案： - 讀取 <code>$SKILLS_HOME/<skill_name>/SKILL.md</code> 來解析現有的 <strong>Chapter Index</strong>, <strong>Topic Index</strong>, metadata（作者、總章節數）以及 <strong>Core Frameworks</strong>。 - 列出 <code>$SKILLS_HOME/<skill_name>/chapters/</code> 裡的所有檔案以找到最大的章節編號 (例如 <code>ch12</code>)。 - 讀取 <code>$SKILLS_HOME/<skill_name>/glossary.md</code>, <code>$SKILLS_HOME/<skill_name>/patterns.md</code>, 以及 <code>$SKILLS_HOME/<skill_name>/cheatsheet.md</code> 以查看已編入索引的術語和框架。</p> <h3 id="2_1">2. 匹配內容並識別修訂與新增<a class="headerlink" href="#2_1" title="Permanent link">¶</a></h3> <p>分析 <code><tempdir>/book_skill_work/full_text.txt</code> 中新提取的文字，以識別新內容是否代表： - <strong>對現有章節的更新/修訂 (Updates/Revisions)</strong>：如果新內容的某個區段直接更新或擴展了現有章節的主題，讀取現有的章節檔案，將新細節合併進去，並重寫該檔案。 - <strong>新增內容 (New additions)</strong>：如果內容引入了新的章節、論文或獨立的區段，在 <code>chapters/</code> 下建立<strong>新的章節摘要檔案</strong>。從現有最大章節編號之後開始編號 (例如，如果現有章節到 <code>ch12</code> 為止，則建立 <code>ch13-*.md</code>, <code>ch14-*.md</code> 等等)。</p> <h3 id="3_2">3. 生成或更新章節摘要檔案<a class="headerlink" href="#3_2" title="Permanent link">¶</a></h3> <p>針對每個新的或修訂的章節： - 讀取新提取文字的對應區段。 - 遵循 <strong>步驟 7</strong> 的格式化指南來建構摘要。 - 在 <code>$SKILLS_HOME/<skill_name>/chapters/</code> 寫入/更新檔案。</p> <h3 id="4_1">4. 合併支援檔案<a class="headerlink" href="#4_1" title="Permanent link">¶</a></h3> <ul> <li><strong>合併 glossary.md</strong>:</li> <li>讀取現有的 <code>$SKILLS_HOME/<skill_name>/glossary.md</code>。</li> <li>從新內容中提取所有新術語和定義（步驟 8 glossary 指南）。</li> <li>將現有術語與新術語合併並按字母順序排列。</li> <li>如果術語已經存在，將新章節/來源參考附加在後面 (例如 <code>**Term** — 定義 (Ch 4, Ch 13)</code>)。</li> <li>將完全合併且按字母排序的列表重寫入 <code>$SKILLS_HOME/<skill_name>/glossary.md</code>。</li> <li><strong>合併 patterns.md</strong>:</li> <li>讀取現有的 <code>$SKILLS_HOME/<skill_name>/patterns.md</code>。</li> <li>從新內容中提取任何新的技巧、演算法或模式。</li> <li>附加新模式，確保格式一致，並保持總長度精簡（2,500 tokens 以內）。</li> <li><strong>合併 cheatsheet.md</strong>:</li> <li>讀取現有的 <code>$SKILLS_HOME/<skill_name>/cheatsheet.md</code>。</li> <li>提取新的比較規則、決策表或參數指南。</li> <li>將它們乾淨地整合進 cheatsheet 結構中。</li> </ul> <h3 id="5-skillmd">5. 重新生成主 SKILL.md<a class="headerlink" href="#5-skillmd" title="Permanent link">¶</a></h3> <p>更新主 skill 檔案 <code>$SKILLS_HOME/<skill_name>/SKILL.md</code>: - <strong>Metadata</strong>: 遞增章節數，更新估算的頁數，並在適當時加入新來源名稱。將 <code>Generated</code> 日期更新為當前日期。 - <strong>Core Frameworks</strong>: 融入來自新內容的最具影響力的心智模型或原則（確保整體檔案維持在 4,000 tokens 以下）。 - <strong>Chapter Index</strong>: 將新章節附加到索引表中，連結到新建立的檔案。 - <strong>Topic Index</strong>: 按字母順序合併新主題。如果現有主題在新的章節中也被涵蓋，請將新章節連結附加至該行 (例如 <code>- **Topic** → ch05, ch13</code>)。</p> <h3 id="6">6. 掃描、清理與報告<a class="headerlink" href="#6" title="Permanent link">¶</a></h3> <p>一旦檔案成功寫入及合併，執行 <strong>步驟 9.5</strong>，接著進行 <strong>步驟 10</strong> 進行清理並列印一份自訂更新報告，總結新加入的章節、合併的術語表項目和更新的索引。如果 skill 資料夾是有 remote 的 git 儲存庫 (透過 <strong>步驟 11</strong> 發佈)，請提供 commit 更新並 push。</p> <hr /> <h2 id="_3">品質規則<a class="headerlink" href="#_3" title="Permanent link">¶</a></h2> <ol> <li><strong>提取結構，而非摘要</strong> — 捕捉具名的框架、確切的表述、反模式；而非章節重點回顧</li> <li><strong>保留作者的精準度</strong> — "The 5 Whys" ≠ "ask why multiple times"；保留確切的命名</li> <li><strong>密度勝於完整度</strong> — 一篇 1,000 tokens 的摘要勝過 10,000 tokens 的摘錄</li> <li><strong>從業人員語氣 (Practitioner voice)</strong> — 寫作格式為 "使用 X 當 Y 發生時"，而不是 "本書解釋了 X"</li> <li><strong>前置載入 SKILL.md</strong> — 壓實會保留前 5,000 tokens；最重要的內容放在最前面</li> <li><strong>章節檔案為按需載入</strong> — 在載入前它們不會計入 skill 預算</li> <li><strong>絕不複製書籍原始文字</strong> — 始終綜合、總結、提取重點訊號</li>
